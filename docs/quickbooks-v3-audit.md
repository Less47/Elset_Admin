# QuickBooks Online V3 audit

Audit and implementation date: 18 September 2026. Local repository only. No production data, Fly credentials, Intuit credentials or real company connection was accessed. The checkout was clean at the start.

## Existing architecture and findings

| Area | Existing implementation | V3 decision |
| --- | --- | --- |
| Provider boundary | `server-accounting-service.js`, provider registry, Xero adapter | Add one QuickBooks adapter; keep service, credentials, locks, operations and mappings shared. |
| Workspace identity | Persistent random `integration_workspace.workspace_id` | Retain it in mapping keys, OAuth state and credential AAD. |
| Credentials | AES-256-GCM; workspace/provider/token-kind AAD; rotated tokens written together | Reuse; persist QuickBooks environment and token-expiry metadata. |
| Concurrency | SQLite provider lease, 120-second expiry, 15-second heartbeat | Retain; block provider-toggle changes while accounting work is in progress. |
| Duplicate prevention | Durable request hash/key plus mapping and remote reconciliation | Reuse operation keys as Intuit `requestid`; do not promise indefinite provider idempotency. |
| Invoice eligibility | `isQualifyingActualInvoice` through `readAccountingInvoice`; sent-history or payment evidence | Reuse actual rule. Drafts and quotes remain ineligible. This task does not invent independent invoice issuance. |
| Customer identity | Local Customer, never Site; billing contact/address | Reuse mapping ownership; stable workspace/customer marker for new QuickBooks Customer. |
| Outbound invoices | Provider-neutral source, manual service operation, exact cents validation | Keep ELSET authoritative; add QuickBooks ItemRef, sales TaxCode and SyncToken translation. |
| Inbound payments | Shared tables, but raw invoice validation and SQL source were Xero-specific | Move Xero translation into its adapter helper; reconcile neutral payment allocations. |
| Payment identity | Schema 10 uniquely identified one external Payment ID | Schema 11 identifies each Payment + Invoice allocation. One QuickBooks payment can legitimately span invoices. |
| Ownership | SQL projection, local CRUD policy and browser normalization assumed `xero` | Use saved provider ownership. Preserve read-only receipts after disabling/disconnecting. |
| Customer Account | Derived from normal invoice and payment rows | No new balance cache, paid-status column or QuickBooks-specific calculation. |
| Webhooks | Xero raw route, durable inbox, retry/lease worker | Keep Xero normalization; share worker with signed QuickBooks CloudEvents. |
| Settings/UI | Xero-specific component and endpoint strings | One `AccountingSettings` and one `InvoiceAccounting`; provider-specific fields only where required. |
| Provider choice | Add-ons could independently enable accounting modules | One enabled provider. Explicitly disable the current add-on first; retain its connection and history. |
| OAuth callback | Current source still required browser auth/session, although a prior fix document existed; `server-app.js` referenced a missing authorizer export | Restore the security design in shared source: public callback, hashed purpose-bound state, live initiating-session/role check, single use, fixed empty 302 redirect. |

The callback's optional returned session must match if present. Without a cookie, the stored initiating session must still exist, be unexpired and belong to an unbanned admin/office user. Untrusted callback user/workspace parameters do not select local ownership. Invalid state does not alter existing connection health. Normal management endpoints still require login, role and mutation-origin checks.

## Financial and operational decisions

- An invoice with any historical mapping to another provider/company cannot be sent again to the new connection. Disabling a provider preserves history and does not silently migrate invoices.
- A QuickBooks workspace is permanently bound to its first environment. Use separate Sandbox and production databases; do not copy Sandbox credentials or mappings into production.
- Existing mapped Customers are read and reused, never overwritten. New names have a stable workspace/customer suffix and Notes marker; no email/name fuzzy matching and no Site sub-customers.
- Only active Service/NonInventory items backed by an active income account are offered. No item, chart account or tax code creation API is implemented.
- Sparse invoice updates preserve unrelated top-level fields. Unsupported line details, payments, credits, voids or externally changed managed fields stop for review. Exact external identity is retained even when returned totals differ.
- Reconcile every mapped invoice connected to a changed QuickBooks payment before one SQLite commit. A moved payment cannot leave both its former and replacement allocation counted after a failed refresh. Unmapped allocations are not imported; they still participate in payment-total validation. Limits: 100 connected invoices and 500 payment identities, then review.
- Payments remain ordinary `payments` rows with provider ownership. Historical manual receipts are retained and block automatic import; credits and ambiguous multi-link lines require review.
- Webhooks persist minimal metadata before HTTP 200, then use the common worker. Leases, restart recovery, bounded exponential retries, Retry-After and paused/review states are shared with Xero. No full payload storage, number-based attachment, background invoice writes or periodic whole-company import.

## Single forward migration

Actual starting version **10**, resulting version **11**. `server-accounting-v3-schema.js` rebuilds only `payments` and `integration_external_payments` to extend their constraints, copying every original column. It adds environment/credential metadata to connections, environment to OAuth states, and external version to mappings. Existing business rows and Xero ciphertext, configuration, IDs, fingerprints, receipts and inbox rows are preserved. The migration ledger, `user_version` and workspace version advance together; late failures roll back. No downgrade path is introduced.
