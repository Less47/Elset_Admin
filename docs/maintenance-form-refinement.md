# Maintenance Add/Edit refinement

Implemented locally. No commit, push, merge, deployment, schema migration, or operational-data mutation was performed. Database writes during verification used temporary fixtures. The earlier dashboard redesign, plan double-click navigation, and recurring Calendar implementation remain in place.

1. **Previous Customer selection.** Add and Edit already shared `MaintenanceEditor` inside `MaintenancePlanPage.jsx`. It used a native customer select, defaulted new plans to the first customer, and combined an editable plan name with a free-text address/datalist. The customer/site utilities also inferred display profiles from billing addresses and old access notes; those profiles are not necessarily saved Site records.

2. **New Customer search.** Both forms now use the same compact `MaintenanceRecordPicker`. It filters the loaded customer collection locally by partial customer name, email, phone, contact name/email/phone, and available site contact/address details. There is no request or workspace reload per keystroke. The combobox supports mouse/touch, Up/Down, Enter, Escape, clear, associated labels, listbox semantics, and active-option announcements. Results have a bounded scroll area, show at most 20 entries, and prompt the user to narrow larger result sets. New plans start without a guessed customer.

3. **Site selection.** The dependent picker offers saved profiles belonging to the selected customer and persists their actual `siteId`. One valid site is selected automatically; multiple sites require a choice. Changing customer clears the previous site and asset association, selects the new customer's sole site when appropriate, and leaves the chosen due date untouched. No-site customers get “No sites found for this customer.” and the existing Add Site route, including the existing unsaved-changes guard. Inferred billing/access-note display profiles are marked internally and excluded from Maintenance; actual Site saves/imports remove that display-only marker. The server checks customer/site ownership and rejects missing, stale, or cross-customer IDs. SQLite already supported IDs through plan extra JSON, but its writer inadvertently omitted `siteId` and `assetId`; those identifiers now survive saves without a schema change.

4. **Automatic Plan Name.** The editable field is replaced by a small read-only Plan preview. A shared naming function produces street plus uppercase suburb, for example `14 Sesame St CAROLINE SPRINGS`. Client and server use the same rule, and submitted arbitrary plan names or addresses cannot override a selected Site. Structured components take priority; ordinary full addresses reuse the existing Service Board formatter, extracted without changing its behavior. Region/country suffixes are removed, with conservative handling of legacy comma-separated and unpunctuated addresses. If the suburb cannot be identified safely, the useful existing address remains as the fallback. Loaded plan names and addresses derive from current linked Site data, so later Site address edits appear on the plan; the stored name snapshot is refreshed on the next plan save. An address edit that supplies no replacement structured components clears stale optional components. This task does not rewrite historic generated jobs.

5. **Exact structured fields.** Street preference: `streetAddress`, then `addressLine1`. Locality preference: `suburb`, then `locality`, then `city`. The fallback uses existing `address`, or `label` when no address is available. The read-only local JSON audit found 52 customers, 66 sites, and 2 plans; those sites used full `address` strings and did not contain the optional structured street/suburb fields. No new address columns or required Customer/Site form fields were introduced. Optional imported components are preserved where already supplied.

6. **Frequency values found.** Code used `monthly`, `quarterly`, `six-monthly`, and `annual`, with previous labels including “6 Monthly” and “Annual.” The local JSON sample contained one `quarterly` plan and one `six-monthly` plan. Neither sample plan contained a `siteId`. Other legacy spellings below are compatibility inputs covered by fixtures; they were not all present in that local sample.

7. **Shared mapping.** `maintenance-frequency.js` is the single source for selector options, display metadata, normalization, and month intervals. It is reused by Add/Edit, dashboard, details, Due Queue, Calendar, recurrence calculations, and newly generated job frequency text. Normalization ignores case and whitespace/hyphen/underscore differences. Unsupported write values are rejected; existing read normalization retains the previous quarterly fallback for unknown values.

   | Internal value retained | UI label | Months | Accepted legacy examples |
   | --- | --- | ---: | --- |
   | `monthly` | Monthly | 1 | Month, 1 Monthly, Every Month |
   | `quarterly` | Quarterly | 3 | Quarter, 3 Monthly, Every 3 Months |
   | `six-monthly` | Biannually | 6 | 6 Monthly, Every 6 Months, Biannual, Semiannually |
   | `annual` | Annually | 12 | Annual, Yearly, 12 Monthly, Every 12 Months |

8. **Biannually means six months.** The existing `six-monthly` recurrence key remains unchanged. A 9 March 2027 anchor produces 9 September 2027, 9 March 2028, and 9 September 2028. `biennial` is rejected; no two-year interpretation was introduced.

9. **Legacy compatibility.** Existing “6 Monthly” plans and recurrence segments display Biannually and calculate at six-month intervals. Annual/Yearly aliases display Annually and calculate at twelve-month intervals. Read hydration does not rewrite stored SQLite frequency rows. Stable segment IDs, occurrence keys, exceptions, and generated/completed history are retained. Legacy plans without a site ID resolve an exact address match within their own customer when available, persisting the ID on a subsequent save. An unmatched legacy plan can retain its unchanged customer/address while editing other fields; replacing that relationship requires a saved Site. No mass plan-name backfill was run.

10. **Calendar regression results.** All 42 existing Calendar browser checks passed in the combined regression run. The Maintenance browser suite also exercises automatic occurrences without generating jobs, one-occurrence moves, future-schedule changes, cancel/escape without writes, optimistic conflicts, one-time job generation and stable links, timezone/DST behavior, and inactive plans. New browser checks verify legacy six-month/annual labels and dates in dashboard, Edit, Calendar chips, and the inspector. Node checks verify unchanged occurrence keys and isolated exceptions across alias normalization, Site changes, and frequency changes. Month arithmetic and the existing recurrence anchor/segment rules were preserved.

12. **Tests added.** Ten Node domain/storage tests cover canonical naming, optional structured fields, saved versus inferred sites, SQLite and JSON server authority, relationship validation, missing versus explicit-zero price, unchanged anchors, and legacy recurrence compatibility. One new API test covers actual IDs, forged display values, aliases, and invalid frequencies. Eight browser tests cover keyboard/contact search and no-site navigation, legacy labels/recurrence, and create/edit persistence at the six required sizes. Existing Maintenance fixtures now select saved Site IDs. The generation regression also asserts the shared Biannually label in new job descriptions.

13. **Validation.** Full Node suite: **226 passed, 0 failed**. Existing Calendar browser checks: **42 passed**. Final Maintenance browser suite: **16 passed, 0 failed** in 38.4 seconds, recorded in `test-results/maintenance-form-browser-complete.log`. Full ESLint passed with no findings, production build passed, and `git diff --check` passed. Vite emitted its existing large-bundle advisory. Early browser failures uncovered ambiguous test selectors, fixture contacts that had not been written into the relational contact table, and the inferred billing-address edge case; the selectors/fixtures and both normalization layers were corrected before the final run. Logs are in the ignored `test-results/maintenance-form-*.log` files.
